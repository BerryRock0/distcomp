# distcomp — LLM-планировщик распределённых вычислений на C

Программа, которая берёт цель на естественном языке, спрашивает у LLM **как её
разложить на шаги**, и затем сама решает, **какой демон на какой удалённой
машине выполнит каждый шаг** — параллельно, с балансировкой по загрузке.

Никаких внешних зависимостей: JSON-парсер, транспорт (UDP/TCP/DTN), движок
llama-архитектуры и HTTP-сервер панели написаны с нуля. Планирование тоже
ведёт локальная модель, разложенная по узлам, поэтому ни ключей, ни внешнего
сервера, ни OpenSSL не нужно.

```
   dcctl run "посчитать закупку 1250*3, доставку 480, поделить на 7"
             │
             ▼
       ┌──────────────┐   модель GGUF разложена по узлам роли shard:
       │ локальная    │   вход → слои → выход, по сети идёт активация
       │    модель    │◄── тот же движок, что и для `llm prompt`
       └──────────────┘   негодный план возвращается модели с причиной
             │
             ▼
       ┌──────────────┐   топологическая сортировка + параллельный запуск
       │  планировщик │   выбор наименее загруженного демона в роли
       └──────────────┘
             │            │            │
             ▼            ▼            ▼
       compute×N      verify        memorize      ← роли назначает он сам
       (разные        (сверка)      (запись
        машины)                       в память)
```

Обмен планировщика с узлами — **UDP** (14-байтовый заголовок + JSON, CRC32).
Причина: тот же код должен работать на микроконтроллере с 32 КБ ОЗУ, где TCP-стека
нет вовсе, а HTTP-сервер — это ещё и слушающий сокет на каждый запрос.

# Установка

## Требования

| Что | Версия | Зачем |
|-----|--------|-------|
| Компилятор C | GCC 8+ или Clang 8+ (C11) | сборка |
| pthreads | стандартная | потоки планировщика и панели |
| make | любой | сборка |
| Python 3 + numpy | 3.6+ | **только для тестов**: эталонная модель GGUF и `discover` в стенде |
| node | любой | необязательно: тест разбирает скрипт панели |

Внешних библиотек нет вообще: JSON-парсер, транспорт UDP/TCP/DTN, движок
llama-архитектуры, веб-сервер и арифметический вычислитель написаны с нуля.
OpenSSL был нужен только для HTTPS к облачному LLM — такого обращения больше
нет, поэтому и библиотеки не нужно.

### Установка зависимостей

```bash
# Debian / Ubuntu / Raspberry Pi OS
sudo apt install build-essential

# Fedora / RHEL
sudo dnf install gcc make

# Alpine
sudo apk add build-base

# macOS (Homebrew)
brew install make
```

## Сборка из исходников

```bash
git clone <адрес репозитория> distcomp      # или скопируйте папку
cd distcomp
make
```

Что появится в `bin/`:

| Файл | Что это |
|------|---------|
| `bin/dcctl` | планировщик и веб-панель |
| `bin/dcd` | узел (вычислитель) для сервера и Raspberry Pi |
| `bin/dcd-lite` | узел для микроконтроллера (~55 КБ вместе с libc) |
| `bin/expr_test` | юнит-тесты вычислителя выражений |

Проверить, что всё собралось:

```bash
make test        # 20 сценариев, ~60 секунд, свой стенд на свободных портах
./bin/dcctl --version
```

Ожидаемый вывод `make test` заканчивается так:

```
-----------------------------------------
пройдено: 120, упало: 0
```

### Кросс-сборка для микроконтроллера

```bash
make lite
make size
```

`make size` печатает размер обычного и lite-узла. Сборка lite — это `-Os`,
буферы в BSS, без `malloc` и потоков.

## Установка готовыми пакетами

### Debian / Ubuntu

```bash
sudo mkdir -p /usr/local/bin
sudo install -m755 bin/dcctl bin/dcd bin/dcd-lite /usr/local/bin/
sudo install -m644 conf/distcomp.conf.example /etc/distcomp.conf.example
# свой конфиг лучше держать в ~/.distcomp.conf — его подхватывают автоматически
```

### systemd: узел как служба

Файл `/etc/systemd/system/distcomp-node.service`:

```ini
[Unit]
Description=distcomp node
After=network-online.target

[Service]
Type=simple
User=distcomp
ExecStart=/usr/local/bin/dcd --port 9101 \
          --tag node-a --state /var/lib/distcomp
Restart=always
RestartSec=2

[Install]
WantedBy=multi-user.target
```

```bash
sudo useradd -r -s /usr/sbin/nologin distcomp
sudo mkdir -p /var/lib/distcomp && sudo chown distcomp /var/lib/distcomp
sudo systemctl enable --now distcomp-node
```

Планировщик в фоне:

```ini
[Unit]
Description=distcomp web panel
After=network-online.target

[Service]
Type=simple
User=distcomp
Environment=OPENAI_API_KEY=sk-...
ExecStart=/usr/local/bin/dcctl web --config /etc/distcomp.conf --host 0.0.0.0 --port 8080
Restart=always

[Install]
WantedBy=multi-user.target
```

### Панель в Docker

```dockerfile
FROM debian:bookworm-slim
COPY bin/dcctl bin/dcd /usr/local/bin/
EXPOSE 8080/udp 8080/tcp 9101-9104/tcp
ENTRYPOINT ["/usr/local/bin/dcctl", "web", "--host", "0.0.0.0"]
```

```bash
docker build -t distcomp .
docker run -d --name distcomp -p 8080:8080 -p 9101-9104:9101-9104/udp distcomp
```

# Первый запуск за 5 минут

## 1. Поднять узлы

На одной машине для проверки:

```bash
mkdir -p ~/dc-state
./bin/dcd --port 9101 --tag local-a --state ~/dc-state &
./bin/dcd --port 9103 --tag local-b --state ~/dc-state &
./bin/dcd --port 9104 --tag local-c --state ~/dc-state &
```

В сети — тот же бинарник на каждой машине, адрес в адресе узла меняется:

```bash
# на raspberry-pi
./dcd --port 9101 --tag pi-1 --state /var/lib/distcomp
# на телефоне с Termux или на ESP32 через UART
./dcd --port 9101 --tag phone --state ./state
```

## 2. Создать конфигурацию

```bash
./bin/dcctl init distcomp.conf
$EDITOR distcomp.conf
```

Минимально рабочее содержимое:

```ini
[llm]
api_key = $OPENAI_API_KEY        # или пусто, если LLM локальная

[role compute]
daemon = 127.0.0.1:9101
daemon = 127.0.0.1:9105          # хотите балансировку — добавьте ещё узлов

[role verify]
daemon = 127.0.0.1:9103

[role memorize]
daemon = 127.0.0.1:9104

[scheduler]
concurrency = 4
retries     = 2
timeout_ms  = 60000
outdir      = runs
```

## 3. Проверить, что всё видно

```bash
./bin/dcctl check
```

```
роль compute   2 узел(ов)
    127.0.0.1:9101  живой,   0 мс, лимит тела 59986 байт, роль любая
    127.0.0.1:9105  живой,   1 мс, лимит тела 59986 байт, роль любая
роль verify    1 узел(ов)
    127.0.0.1:9103  живой,   0 мс, лимит тела 59986 байт, роль любая
роль memorize  1 узел(ов)
    127.0.0.1:9104  живой,   0 мс, лимит тела 59986 байт, роль любая

проверено 4 узлов, проблем 0
```

Если узлов не видно — они не запущены, или в адресе ошибка. Быстрая проверка
одного узла: `./bin/dcd --port 9101` должен напечатать
`порт 9101` и молча работать дальше. Про роли он больше не спрашивает:
их назначает распределитель.

## 4. Посмотреть план, не выполняя

```bash
./bin/dcctl plan "стоимость закупки 1250*3 и доля (1250*3+480)/7"
```

LLM вернёт шаги; вы увидите, какие роли и узлы подобраны, и ничего не выполнится.

## 5. Выполнить

```bash
./bin/dcctl run "стоимость закупки 1250*3 и доля (1250*3+480)/7"
```

```
Запуск плана (4 шагов, параллелизм 4, попыток на шаг 3)

  [»] s1   compute  192.168.1.10         стоимость закупки (98 байт)
  [»] s2   compute  192.168.1.11         доля части (114 байт)
  [+] s1   compute  192.168.1.10             -> 3750  (1 мс)
  [+] s2   compute  192.168.1.11             -> 604.2857143  (1 мс)
  [»] s3   verify   192.168.1.10         сверка суммы (193 байт)
  [+] s3   verify   192.168.1.10             -> OK  (0 мс)
  [»] s4   memorize 192.168.1.12         итог (175 байт)
  [+] s4   memorize 192.168.1.12             -> записано #4  (0 мс)

Итог:
  + s1   compute   192.168.1.10    3750
  + s2   compute   192.168.1.11    604.2857143
  + s3   verify    192.168.1.10    OK
  + s4   memorize  192.168.1.12    записано #4

Все шаги выполнены.
Каталог запуска: runs/20250114-101530
```

Артефакты запуска: `runs/<метка>/plan.json` (что собирались делать) и
`result.json` (что получилось).

## 6. Открыть панель

```bash
./bin/dcctl web --port 8080
```

Браузер: <http://localhost:8080>.

# Модель, которая планирует

Без модели планировщик не понимает естественный язык. Но просить её больше
некого: модель лежит в файле GGUF на диске, её веса раскладываются по узлам
роли `shard`, а по сети между ними идёт активация. Ключей нет, адресов нет,
TLS нет — и работает это при выключенной сети.

## Что нужно

| Что | Зачем |
|-----|-------|
| GGUF-файл архитектуры `llama` (LLaMA, Mistral, Qwen2 — родственники) | сама модель |
| Тензоры F32 или F16 | квантование (Q4/Q8) пока не разбирается |
| Минимум **три** узла роли `shard` | вход, слои и выход обязаны быть на разных узлах |
| Инструктная модель среднего размера | разложенная на несколько слов она отвечает связно |

Словарь здесь важнее, чем кажется. Системный промпт планировщика — примерно
шестьсот токенов у нормальной модели и несколько тысяч у модели с крошечным
словарём. Планировщик считает промпт по-настоящему, токен за токеном, и если
контекста не хватает — говорит об этом прямо, а не обрезает инструкцию.

## Разложить модель по узлам

```bash
./bin/dcd --port 9101 --tag in  --free-mem 450000 --state state &
./bin/dcd --port 9102 --tag big --free-mem 450000 --state state &
./bin/dcd --port 9103 --tag out --free-mem 450000 --state state &

./bin/dcctl llm info model.gguf      # что во что ляжет
./bin/dcctl llm deploy model.gguf    # залить веса
```

Конфигурация:

```ini
[llm]
model_file = model.gguf
n_ctx      = 1024      # токенов контекста; больше — узлам нужно больше памяти
max_new    = 512       # сколько токенов модель может нагенерировать

[role shard]
daemon = 127.0.0.1:9101
daemon = 127.0.0.1:9102
daemon = 127.0.0.1:9103
```

Проверка:

```
$ ./bin/dcctl llm
модель: model.gguf
узлы:   shard

архитектура:    llama
слоёв:          28
размер вектора: 1536
словарь:        151936
контекст:       1024 токенов
размер файла:   3100000000 байт

Раскладка модели по устройствам:

  стадия                требует     узел
  вход (эмбеддинг) 295000       127.0.0.1:9101
  слои 0..13        1480000000   127.0.0.1:9102
  слои 14..27       1480000000   127.0.0.1:9103
  выход (голова)    300000       127.0.0.1:9104

готово: план можно строить локально — ключи и внешний сервер не нужны.
```

## Планирование

После этого `run` работает как раньше — просто вместо чужого сервера
спрашивает вашу же разложенную модель:

```bash
./bin/dcctl run "стоимость закупки 1250*3 и доля (1250*3+480)/7"
```

Планировщик по-прежнему проверяет план тем же кодом, что и вручную написанный.
Если модель вернула негодный план (цикл, неизвестная роль, обрезанный ответ),
причина возвращается ей же, и она пробует исправить — две попытки:

```
ERR   план от модели отклонён: в графе шагов есть цикл (1 из 4 шагов упорядочимы)
info  прошу модель исправить план (попытка 2)
```

## Без модели

```bash
./bin/dcctl run --no-llm "посчитать 1250*3 и долю (1250*3+480)/7"
```

Эвристика вытащит из цели арифметические выражения и построит
`compute… → verify → memorize`. Подходит для тестов и работы без модели.
`--strict` запрещает молчаливый откат на неё: если модель настроена, но
план не годится, будет ошибка, а не тихо выполненный чужой план.

## Что делать, если модель не пошла

```
info  промпт 4221 токенов, ответ до 96, нужно контекста 4325
ERR   промпт и ответ требуют 4325 токенов контекста, а больше 4096 узлы не держат
```

Значит, словарь модели слишком мелкий: на каждый знак приходится токен, и
инструкция не влезает ни в какой разумный контекст. Берите модель с нормальным
словарём — Qwen2.5-Instruct, а не тестовую заглушку. Размер промпта виден
по `-v`, и он считается токен за токеном, а не на глаз.

Другие частые причины:

| Симптом | Что делать |
|---------|-----------|
| `не задана модель` | `model_file` в секции `[llm]` |
| `нужно минимум 3 узла роли shard` | вход, слои и выход должны быть на разных устройствах |
| `узел не вмещает ни одного слоя` | поднимите `--free-mem` или добавьте устройство |
| `модель не разложилась по узлам` | контексту не хватает памяти: снизьте `n_ctx` |

# Работа в командной строке

## Команды `dcctl`

| Команда | Что делает |
|---------|-----------|
| `init [ПУТЬ]` | создать образец конфигурации |
| `roles` | показать назначение ролей, лимиты и статистику узлов |
| `check` | опросить узлы: живы ли, что умеют, сколько памяти отдают |
| `discover [СЕК]` | найти узлы, объявляющие себя по широковещанию |
| `llm` | спросить у LLM список моделей: сервер жив, модель на месте |
| `plan "цель"` | построить план и показать, ничего не выполняя |
| `run "цель"` | построить план и выполнить |
| `run -f план.json` | выполнить готовый план |
| `replay МЕТКА` | повторить прошлый запуск по сохранённому плану |
| `runs` | список прошлых запусков с итогом |
| `llm` | готов ли планировщик: модель, раскладка, парк узлов |
| `llm info\|deploy\|prompt ФАЙЛ` | модель llama (GGUF), разложенная по памяти устройств |
| `web [--host АДРЕС] [--port ПОРТ]` | веб-панель |

## Опции

```
  -c, --config ФАЙЛ     конфигурация (по умолчанию ./distcomp.conf, ~/.distcomp.conf)
      --role РОЛЬ=URL    закрепить узел за ролью (можно повторять); без этого
                        распределитель сам выбирает из пула рабочих
  -f, --plan-file ФАЙЛ  исполнить готовый план
  -j, --concurrency N   одновременно выполняемых шагов
      --retries N       повторов при ошибке узла
      --timeout МС      таймаут одного узла
      --no-llm          не обращаться к LLM, построить план эвристикой
      --strict          не откатываться на эвристику при ошибке LLM
  -o, --out ДИР         куда сохранять plan.json / result.json
      --host АДРЕС      адрес веб-панели (по умолчанию 0.0.0.0)
      --port ПОРТ       порт веб-панели (по умолчанию 8080)
  -v, --verbose         подробный лог
      --color УРОВЕНЬ   цвет вывода: auto | always | never
  -V, --version         версия
  -h, --help            эта справка
```

**Глобальные опции пишутся до команды.** Исключение — `web`: у панели свои
опции, и привычно писать `dcctl web --port 8080`.

## Коды возврата

| Код | Значение |
|-----|----------|
| `0` | все шаги выполнены |
| `1` | есть незавершённые шаги |
| `2` | ошибка в аргументах |
| `3` | проблема с конфигурацией или недоступен сервис |
| `4` | план отклонён проверкой |

## Цветной вывод

Цвет включается сам, если stdout — терминал. В файле или в конвейере
управляющих кодов нет, поэтому вывод остаётся пригодным для `grep`:

```bash
./bin/dcctl run "..."            # в терминале — с цветом
./bin/dcctl run "..." | grep OK  # в конвейере — чистый текст
./bin/dcctl --color never run "…"
NO_COLOR=1 ./bin/dcctl run "…"
```

## История и повтор

```bash
$ ./bin/dcctl runs
Запуски в runs (новые сверху):

  20250114-104512   шагов 4 из 4   стоимость закупки и доля части
  20250114-101530   шагов 2 из 2   посчитать 6*7

Повторить: dcctl replay 20250114-104512

$ ./bin/dcctl replay 20250114-101530     # тот же план, другие узлы, свежий результат
```

Повтор полезен, когда узлы изменились: план уже утверждён, LLM не вызывается,
шаги просто уходят на те узлы, что живы сейчас.

## Свой план

Никто не мешает выполнить план, написанный руками:

```bash
cat > my.json <<'EOF'
{"goal":"проверка своими руками","steps":[
 {"id":"c1","role":"compute","title":"цена","payload":"100*3","deps":[]},
 {"id":"v1","role":"verify","title":"сверка","payload":"300","deps":["c1"]},
 {"id":"m1","role":"memorize","title":"итог","payload":"записать","deps":["v1"]}]}
EOF
./bin/dcctl run -f my.json
```

Шаг можно закрепить за конкретным узлом полем `node` — так делается раскладка
модели:

```json
{"id":"s1","role":"compute","title":"...","payload":"...","deps":[],"node":"10.0.0.7:9101"}
```

Перед выполнением план проверяется: роли назначены узлам, зависимости
существуют, граф ацикличен. Любое нарушение — понятная ошибка вместо молчаливого
неверного результата.

## Автоматизация


# Конфигурация

Файл `distcomp.conf` в текущем каталоге или `~/.distcomp.conf`. Ключ `-c`
указывает другой путь.

```ini
[llm]
model_file   = model.gguf              # GGUF, который раскладывается по узлам shard
n_ctx        = 1024                    # токенов контекста (потолок 4096)
max_new      = 512                     # сколько токенов модель может нагенерировать
payload_mode = expr                    # expr | free

[role compute]
daemon = 10.0.0.1:9101                 # host:port — транспорт UDP
daemon = 10.0.0.2:9101
daemon = tcp://10.0.0.3:9101           # тот же узел через TCP
daemon = dtn://10.0.0.4:9101           # через DTN: store-and-forward при обрывах

[role verify]
daemon = 10.0.0.4:9103

[role memorize]
daemon = 10.0.0.5:9104

[role shard]                           # устройства, на которых лежат части модели
daemon = 10.0.0.6:9102

[scheduler]
concurrency = 4      # одновременно выполняемых шагов
retries     = 2      # повторов при ошибке демона
timeout_ms  = 60000  # таймаут одного узла
backoff_ms  = 500    # пауза перед повтором (умножается на номер попытки)
outdir      = runs   # куда писать plan.json и result.json
```

## Ключи `[llm]`

| Ключ | Значения | Смысл |
|------|----------|-------|
| `model_file` | путь | GGUF-файл модели; пусто — план строит эвристика |
| `n_ctx` | число | сколько токенов контекста держат узлы; 0 — подобрать под промпт, потолок 4096 |
| `max_new` | число | сколько токенов модель может нагенерировать на ответ |
| `payload_mode` | `expr` \| `free` | что такое `payload`: арифметика или свободный текст |

Транспорт задаётся схемой в адресе узла:

| Схема | Что это |
|-------|---------|
| без схемы, `host:port` | UDP — по умолчанию, работает даже на микроконтроллере |
| `tcp://host:port` | надёжный поток; лимита на размер сообщения нет |
| `dtn://host:port` | store-and-forward: сообщения копятся на диске и досылаются после обрыва |

Схему можно ставить у любого узла любой роли — и у вычислителя, и у устройства
с моделью.

## Ключи `[scheduler]`

| Ключ | Смысл |
|------|-------|
| `concurrency` | сколько шагов одновременно; больше — быстрее, но нагрузка на сеть |
| `retries` | сколько раз повторить шаг при ошибке узла |
| `timeout_ms` | сколько ждать ответа одного узла |
| `backoff_ms` | пауза перед повтором, равен `backoff_ms × номер попытки` |
| `outdir` | каталог для `plan.json` и `result.json` |

## Тяжёлая нода и ядра

| ключ | где | смысл |
|---|---|---|
| `threads` | `[node]`, `daemon = ... threads=N` | сколько ядер отдать под счёт. 0 — все свободные (по умолчанию), 1 — одно. |

Тяжёлая нода — та, что держит веса модели. Она считает на всех свободных
ядрах; узлы, которые только считают выражения, в этом не участвуют: работа
там мелкая, а разбиение дороже самой работы.

Переменная окружения `DC_THREADS` перекрывает значение из конфигурации —
удобно для замеров.

## Роли

Роли в конфигурации можно назвать как угодно (`[role gpu]`), но тогда узел должен
уметь обслуживать именно это имя. Встроенный `dcd` понимает четыре:

| Роль | Что делает |
|------|-----------|
| `compute` | считает арифметическое выражение из `payload` |
| `verify` | сверяет: `payload = all` — все результаты непустые; число — один из результатов должен совпасть |
| `memorize` | дописывает JSONL-запись в `state/memory.log` |
| `shard` | держит свои слои весов и считает ими по активациям |

# Узлы: запуск и роли

## Как узлы находятся сами

Узел рассылает объявление при старте и раз в `--hello-interval` секунд. Чтобы не
ждать, планировщик спрашивает сеть активным запросом:

```bash
$ ./bin/dcctl discover 5
Слушаю объявления узлов 5 с (Ctrl-C — прервать)…
  192.168.0.101   :9101   pi-1     compute,verify      лимит  59986 байт  x86_64
  192.168.0.101   :9102   mcu-01   compute,memorize    лимит   1024 байт  x86_64

найдено объявлений: 2
добавьте нужные строки в конфигурацию, например:
  [role compute]
  daemon = 192.168.1.50:9101
```

Скопированные строки вставьте в конфигурацию — или назначьте узлы из панели.

## Как выбирается узел

- Шаги с готовыми зависимостями стартуют одновременно, максимум `concurrency`.
- Внутри роли берётся узел с наименьшим числом текущих задач; при равенстве —
  по кругу, так что простаивающие узлы загружаются равномерно.
- Узел, который не примет задачу по размеру, исключается заранее: лимит
  известен из первого PING.
- Упавший узел не убивает задачу: идёт повтор с задержкой, и на следующей
  попытке шаг может взять другой узел той же роли.

## Тяжёлый узел берёт все свободные ядра

Почти всё время узел с моделью проводит в `matvec` — умножении матрицы на
вектор. Работа в нём однородна по выходу: каждая строка считается своей
цепочкой сложений и ни на другую не смотрит. Строки и раздаются потокам.

Числа от этого не меняются ни на бит: порядок сложений внутри строки тот же,
меняется только то, кто её считает. Поэтому сверка с эталоном остаётся
токен в токен.

По умолчанию узел берёт все свободные ядра — держать машину наполовину
простаивающей ради экономии незачем. На 16 ядрах Xeon движок считает вшестеро
быстрее, а конвейер из четырёх узлов на одной машине проходит задачу вдвое
быстрее по времени при том же расходе CPU.

```bash
./bin/dcd --port 9101 --threads 0     # все ядра (по умолчанию)
./bin/dcd --port 9101 --threads 1     # как было: одно ядро
./bin/dcd --port 9101 --threads 4     # четыре
```

Из конфигурации — глобально или на конкретный узел:

```ini
[node]
threads = 0                  # все ядра; 1 — одно, 4 — четыре

[role shard]
daemon = 10.0.0.7:9101 threads=2    # этому узлу — два
```

Переменная окружения `DC_THREADS` действует на оба: удобно, когда надо
посмотреть, во сколько обходится однопоточный счёт.

Число потоков видно и в отчёте — «сколько ядер взято» стоит рядом с лимитом
тела, и по нему сразу понятно, что узел не простаивает:

```
$ dcctl check
роль shard    4 узел(ов)
    10.0.0.7:9101  живой,   0 мс, лимит тела 59986 байт, 16 потоков, под модель 268435456 байт
```

Пул поднимается лениво: узел, который считает только выражения, до него не
доходит вовсе, а сборка для микроконтроллеров (`make lite`) не поднимает
его никогда — там ядро одно, и лишние стеки только вредны.

## Роль назначает распределитель

Раньше узел объявлял, кем он будет: `--role compute --role verify`. Это было
лишнее — роль всё равно приходит в теле задачи, и узел исполняет именно её.

Теперь рабочий про роль не знает вовсе. Он сообщает только то, что о нём
действительно нужно знать, — свою мощь:

```bash
./bin/dcd --port 9101 --state state      # и всё
```

А распределитель сам спрашивает сеть, складывает найденных рабочих в пул и
назначает роль на каждую задачу отдельно: сегодня этот узел посчитал, завтра
проверил, послезавтра держал слои модели. Сколько работы достанется —
тоже его решение: узлы с большей памятью получают больше слоёв.

Конфигурация при этом становится необязательной. Если роли не описаны,
рабочие берутся из пула:

```bash
./bin/dcd --port 9101 & ./bin/dcd --port 9102 & ./bin/dcd --port 9103 &
dcctl run 'посчитать стоимость закупки 1250*3'
# найдено рабочих: 3
```

Секции `[role ...]` тоже работают — ими узел закрепляют за ролью намертво,
когда конкретную машину надо оставить на конкретной работе.

# Модель, разложенная по устройствам

Вес модели — почти целиком VRAM. Модель, не помещающаяся в Raspberry Pi с 8 ГБ,
раскладывается на него и на две платы ESP32: слои режутся, кладутся на устройства
по их свободной памяти, а по сети идёт не модель, а активация.

Здесь это работает на настоящей модели: читается GGUF-файл архитектуры llama
(RMSNorm, RoPE, grouped-query attention, SwiGLU, KV-кэш, BPE-токенизатор),
движок считает шаг внимания и MLP, а планировщик режет сеть на стадии и раскладывает
их по узлам роли `shard`.

## Как устроен конвейер

Модель режется на три вида стадий:

- **вход (эмбеддинг)** — таблица `token_embd`, токен превращается в вектор;
- **слои** — связный диапазон блоков `blk.N.*` (внимание + MLP);
- **выход (голова)** — `output_norm` и `output.weight`, вектор превращается в логиты.

Между стадиями по сети ходит только вектор активации (для этой модели — 64 float),
а не веса. Каждый узел держит ровно один контекст движка, поэтому вход, слои и выход
обязаны жить на разных устройствах — конвейеру нужно **минимум три узла**. Слои
делятся между средними узлами поровну, но с оглядкой на объявленную память: узел,
которому не хватает места на лишний слой, получает меньше.

## Три команды

```bash
./bin/dcctl llm info   model.gguf              # раскладка по узлам
./bin/dcctl llm deploy model.gguf              # раздать веса по узлам
./bin/dcctl llm prompt model.gguf "текст" 8    # генерация с проверкой
```

Устройства берутся из секции `[role shard]`, память — из ответа на PING.
`llm` — основное имя, `shard` — псевдоним; старые подкоманды `shard gen/run`
(демо-формат `DCSH`) больше не используются.

## Сверка

**Сверка обязательна и всегда выполняется.** Планировщик считает ту же модель
у себя целиком (все три стадии подряд, на общем KV-кэше) и на каждом шаге
сравнивает выбранный токен с тем, что вернул конвейер. Ненулевое расхождение
означает, что где-то потерялись веса или активация, и об этом сказано прямо.

Проверить можно и независимо от C-кода — тем же numpy-эталоном, которым
собиралась модель:

```bash
python3 scripts/gguf_expected.py --prompt distcomp --tokens 8
# -> 171 16 66 120 167 151 248 134
```

## Формат модели

Читается GGUF версии 3, архитектура `llama`. Поддерживаются тензоры F32 и F16;
квантование (Q4/Q8) пока не разбирается. Из метаданных берутся `n_layer`, `n_embd`,
`n_head`, `n_head_kv`, `n_ff`, `n_vocab`, `context_length`, `rope.freq_base`,
`rms_eps`. Тензоры стадии — это `token_embd` (вход), `blk.N.*` (слои),
`output_norm` + `output` (выход); остальные в раскладку не попадают.

## Границы

Движок — своя реализация llama-архитектуры (RMSNorm, RoPE, GQA, SwiGLU, KV-кэш),
а не llama.cpp. Механика раскладки, заливки и пересылки активаций — настоящая.
Квантованные GGUF и другие архитектуры (qwen, gemma и т.п.) пока не поддержаны:
нужны соответствующие тензоры и правила RoPE.

# Маленькие устройства

```bash
make lite     # -> bin/dcd-lite
make size
```

Сборка lite: без потоков, без `malloc` (все буферы в BSS), `-Os`, дейтаграмма
1200 байт, приём тела 1024 байта, пул под модель 8 КБ. Бинарник — около 55 КБ
вместе с libc. Цель: SAMD51, RP2040, ESP32, STM32.

Транспорт тут только UDP, и это не упрощение: потоковые TCP и DTN на таких
контроллерах всё равно некуда. Флаги `--tcp` и `--dtn` lite-сборка принимает и
честно отказывает, вместо того чтобы молча проигнорировать.

Что планировщик знает про маленький узел и не делает:

- не пришлёт задачу тяжелее лимита тела узла;
- не положит в него больше весов, чем тот сам объявил;
- смешанный парк работает сам: в одной роли может быть и сервер, и плата,
  мелкие шаги распределятся по обоим, тяжёлые уйдут туда, где есть лимит.

Смешанный парк проверяется в тестах (сценарий 14) и в демо-стенде.

# Что делать, если не работает

| Симптом | Причина и что делать |
|---------|----------------------|
| `ни одной роли не обеспечено узлом` | в конфигурации нет ни одного `daemon`; проверьте `dcctl roles` |
| `узел не слушает порт (ICMP unreachable)` | на этой машине узел не запущен или порт занят: `ss -ulnp \| grep 9101` |
| `задача N байт не помещается ни в один узел роли …` | все узлы роли маленькие; добавьте узел побольше или разбейте шаг |
| `шаг закреплён за узлом …, но он не взял задачу` | узел изменился или перегружен; уберите `node` из шага или поправьте адрес |
| `в графе шагов есть цикл` | так бывает в плане от модели: план не выполнен, поправьте `deps` и повторите |
| `план не является корректным JSON` | смотрите сырой ответ модели: `./bin/dcctl -v plan "…"` |
| `не задана модель` | укажите `model_file` в секции `[llm]` |
| `нужно минимум 3 узла роли shard` | вход, слои и выход обязаны быть на разных устройствах |
| `промпт и ответ требуют N токенов контекста` | словарь модели слишком мелкий: инструкция не влезает ни в какой разумный контекст; возьмите модель типа Qwen2.5-Instruct |
| `узел не вмещает ни одного слоя` | поднимите `--free-mem` или добавьте устройство |
| `модель не разложилась по узлам` | контексту не хватает памяти: снизьте `n_ctx` в `[llm]` |
| `в узле не хватает памяти для слоя` | поднимите `--free-mem` или добавьте устройство |
| в панели «предыдущий запуск ещё идёт» | дождитесь конца или откройте другую вкладку; запуски по одному |
| узлы не находятся через `discover` | широковещание может быть запрещено сетью; укажите узлы вручную |

Подробный лог: `./bin/dcctl -v …`. Проверить узлы по одному: `./bin/dcctl check`.

# Подробности

## Роли и что делает встроенный узел

| Роль | Что делает |
|------|-----------|
| `compute` | считает арифметическое выражение из `payload` |
| `verify` | сверяет: `payload = all` — все результаты непустые; число — один из результатов должен совпасть |
| `memorize` | дописывает JSONL-запись в `state/memory.log` |
| `shard` | держит свои слои весов и считает ими по активациям предыдущего |

## Формат плана

LLM обязана вернуть такой JSON (клиент снимает markdown-ограждения сам):

```json
{
  "goal": "стоимость закупки и доля части",
  "steps": [
    {"id":"s1","role":"compute","title":"стоимость закупки","payload":"1250*3","deps":[]},
    {"id":"s2","role":"compute","title":"доля части","payload":"(1250*3+480)/7","deps":[]},
    {"id":"s3","role":"verify","title":"сверка","payload":"3750","deps":["s1","s2"]},
    {"id":"s4","role":"memorize","title":"итог","payload":"итоговая сумма","deps":["s3"]}
  ]
}
```

Результаты шагов передаются зависимым в поле `context`, поэтому `verify` имеет
под рукой то, что вычислили `compute`.

## Протокол демона

Узел — это любой процесс, который отвечает на UDP-порт и понимает заголовок
из `src/udp.h`. Заголовок 14 байт, big endian:

```
  смещение  размер  поле
     0        2     magic = 0x4443 ('D','C')
     2        1     версия протокола (2)
     3        1     тип сообщения
     4        2     флаги (бит 0 — тело в JSON)
     6        4     длина тела
    10        4     CRC32 тела
    14        N     тело (JSON, UTF-8)
```

Типы: `REQUEST=1`, `RESPONSE=2`, `PING=3`, `PONG=4`, `HELLO=5`, `WELCOME=6`.

Запрос:

```json
{"role":"compute","title":"...","payload":"1250*3","attempt":1,
 "context":[{"from":"s1","role":"compute","output":"3750"}]}
```

Ответ:

```json
{"ok":true,"output":"3750","detail":"1250*3 = 3750",
 "node":"pi-1","max_body":59986,"free_mem":1048576,"roles":"compute,verify"}
```

`ok:false` означает провал шага: планировщик повторит его `retries` раз, а
зависимые шаги пометит заблокированными. Ответ на `PING` — `PONG` с тем же
набором полей.

## Формат выражений

`payload` в режиме `payload_mode = expr` — арифметика: `+ - * / % ^`, скобки,
унарный минус, функции `sqrt abs min max pow floor ceil round sign sin cos tan
asin acos atan exp log log2 log10 atan2`, константы `pi e tau`, запятая как
разделитель аргументов функции и `_` как разделитель разрядов внутри числа
(`1_000_000`). Пример: `(1250*3+480)/7`.

Если `payload_mode = free`, LLM получает другое указание и `payload` становится
произвольным текстом — этот режим для демонов, которые занимаются чем-то
сложением арифметики.

## Планирование: модель, починка и эвристика

Модели отправляется один системный промпт, в котором перечислены доступные
роли, их узлы и реальные лимиты тела. Размер промпта считается по
токенизатору заранее — токен за токеном, а не «на глаз»: у модели со
словарём в 256 слов каждый знак — токен, и грубая оценка врёт в семь раз.

Дальше план **проверяется тем же кодом, что и вручную принятый**: цикл,
несуществующая зависимость, неизвестная роль, пустой ответ — всё это не «план»,
а отказ.

На отказ модель не выбрасывается: ей отправляется её собственный прошлый ответ
и точная причина, и она пробует исправить. Попыток две. Только после этого —
эвристика, и то лишь если не задан `--strict`.

## Как распределяется нагрузка

Два разных распределения, и их не надо путать:

- **Шаги плана** между узлами своей роли: с готовыми зависимостями стартуют
  одновременно, максимум `concurrency`; внутри роли берётся узел с наименьшим
  числом текущих задач, при равенстве — по кругу. Узел, который не примет
  задачу по размеру, исключается заранее.
- **Модель** между узлами роли `shard`: слои режутся и раскладываются по их
  объявленной свободной памяти, по сети идёт активация, а не веса.

Упавший узел не убивает задачу: повтор с задержкой, и на следующей попытке
шаг может взять другой узел той же роли.
