# distcomp — LLM-планировщик распределённых вычислений на C

Программа, которая берёт цель на естественном языке, спрашивает у LLM **как её
разложить на шаги**, и затем сама решает, **какой демон на какой удалённой
машине выполнит каждый шаг** — параллельно, с балансировкой по загрузке.

Никаких внешних зависимостей кроме OpenSSL и pthreads: HTTP-клиент, JSON-парсер,
транспорт UDP и HTTP-сервер панели написаны с нуля.

```
   dcctl run "посчитать закупку 1250*3, доставку 480, поделить на 7"
             │
             ▼
       ┌──────────────┐   план: шаги, роли, зависимости
       │  LLM-вызов   │◄── OpenAI-совместимый API, локальный или облачный
       └──────────────┘   негодный план возвращается модели с причиной
             │
             ▼
       ┌──────────────┐   топологическая сортировка + параллельный запуск
       │  планировщик │   выбор наименее загруженного демона в роли
       └──────────────┘
             │            │            │
             ▼            ▼            ▼
       compute×N      verify        memorize      ← роли выбираете вы
       (разные        (сверка)      (запись
        машины)                       в память)
```

Обмен планировщика с узлами — **UDP** (14-байтовый заголовок + JSON, CRC32).
Причина: тот же код должен работать на микроконтроллере с 32 КБ ОЗУ, где TCP-стека
нет вовсе, а HTTP-сервер — это ещё и слушающий сокет на каждый запрос.

# Установка

## Требования

| Что | Версия | Зачем |
|-----|--------|-------|
| Компилятор C | GCC 8+ или Clang 8+ (C11) | сборка |
| OpenSSL | 1.1+ (только библиотека) | HTTPS к облачной LLM |
| pthreads | стандартная | потоки планировщика и панели |
| make | любой | сборка |
| Python 3 | 3.6+ | **только для тестов** и `discover` в стенде |
| node | любой | необязательно: тест разбирает скрипт панели |

Внешних библиотек больше нет: HTTP-клиент, JSON-парсер, UDP-транспорт, веб-сервер
и арифметический вычислитель написаны с нуля.

### Установка зависимостей

```bash
# Debian / Ubuntu / Raspberry Pi OS
sudo apt install build-essential libssl-dev

# Fedora / RHEL
sudo dnf install gcc make openssl-devel

# Alpine
sudo apk add build-base openssl-dev

# macOS (Homebrew)
brew install openssl pkg-config
```

## Сборка из исходников

```bash
git clone <адрес репозитория> distcomp      # или скопируйте папку
cd distcomp
make
```

Что появится в `bin/`:

| Файл | Что это |
|------|---------|
| `bin/dcctl` | планировщик и веб-панель |
| `bin/dcd` | узел (вычислитель) для сервера и Raspberry Pi |
| `bin/dcd-lite` | узел для микроконтроллера (~45 КБ вместе с libc) |
| `bin/expr_test` | юнит-тесты вычислителя выражений |

Проверить, что всё собралось:

```bash
make test        # 20 сценариев, ~60 секунд, свой стенд на свободных портах
./bin/dcctl --version
```

Ожидаемый вывод `make test` заканчивается так:

```
-----------------------------------------
пройдено: 105, упало: 0
```

### Кросс-сборка для микроконтроллера

```bash
make lite
make size
```

`make size` печатает размер обычного и lite-узла. Сборка lite — это `-Os`,
буферы в BSS, без `malloc` и потоков.

## Установка готовыми пакетами

### Debian / Ubuntu

```bash
sudo mkdir -p /usr/local/bin
sudo install -m755 bin/dcctl bin/dcd bin/dcd-lite /usr/local/bin/
sudo install -m644 conf/distcomp.conf.example /etc/distcomp.conf.example
# свой конфиг лучше держать в ~/.distcomp.conf — его подхватывают автоматически
```

### systemd: узел как служба

Файл `/etc/systemd/system/distcomp-node.service`:

```ini
[Unit]
Description=distcomp node
After=network-online.target

[Service]
Type=simple
User=distcomp
ExecStart=/usr/local/bin/dcd --role compute --role verify --port 9101 \
          --tag node-a --state /var/lib/distcomp
Restart=always
RestartSec=2

[Install]
WantedBy=multi-user.target
```

```bash
sudo useradd -r -s /usr/sbin/nologin distcomp
sudo mkdir -p /var/lib/distcomp && sudo chown distcomp /var/lib/distcomp
sudo systemctl enable --now distcomp-node
```

Планировщик в фоне:

```ini
[Unit]
Description=distcomp web panel
After=network-online.target

[Service]
Type=simple
User=distcomp
Environment=OPENAI_API_KEY=sk-...
ExecStart=/usr/local/bin/dcctl web --config /etc/distcomp.conf --host 0.0.0.0 --port 8080
Restart=always

[Install]
WantedBy=multi-user.target
```

### Панель в Docker

```dockerfile
FROM debian:bookworm-slim
RUN apt-get update && apt-get install -y --no-install-recommends \
        ca-certificates libssl3 && rm -rf /var/lib/apt/lists/*
COPY bin/dcctl bin/dcd /usr/local/bin/
EXPOSE 8080/udp 8080/tcp
ENTRYPOINT ["/usr/local/bin/dcctl", "web", "--host", "0.0.0.0"]
```

```bash
docker build -t distcomp .
docker run -d --name distcomp -p 8080:8080 -p 9101-9104:9101-9104/udp distcomp
```

# Первый запуск за 5 минут

## 1. Поднять узлы

На одной машине для проверки:

```bash
mkdir -p ~/dc-state
./bin/dcd --role compute  --port 9101 --tag local-a --state ~/dc-state &
./bin/dcd --role verify   --port 9103 --tag local-b --state ~/dc-state &
./bin/dcd --role memorize --port 9104 --tag local-c --state ~/dc-state &
```

В сети — тот же бинарник на каждой машине, адрес в адресе узла меняется:

```bash
# на raspberry-pi
./dcd --role compute --port 9101 --tag pi-1 --state /var/lib/distcomp
# на телефоне с Termux или на ESP32 через UART
./dcd --role compute --port 9101 --tag phone --state ./state
```

## 2. Создать конфигурацию

```bash
./bin/dcctl init distcomp.conf
$EDITOR distcomp.conf
```

Минимально рабочее содержимое:

```ini
[llm]
api_key = $OPENAI_API_KEY        # или пусто, если LLM локальная

[role compute]
daemon = 127.0.0.1:9101
daemon = 127.0.0.1:9105          # хотите балансировку — добавьте ещё узлов

[role verify]
daemon = 127.0.0.1:9103

[role memorize]
daemon = 127.0.0.1:9104

[scheduler]
concurrency = 4
retries     = 2
timeout_ms  = 60000
outdir      = runs
```

## 3. Проверить, что всё видно

```bash
./bin/dcctl check
```

```
роль compute   2 узел(ов)
    127.0.0.1:9101  живой,   0 мс, лимит тела 59986 байт, роли: compute
    127.0.0.1:9105  живой,   1 мс, лимит тела 59986 байт, роли: compute
роль verify    1 узел(ов)
    127.0.0.1:9103  живой,   0 мс, лимит тела 59986 байт, роли: verify
роль memorize  1 узел(ов)
    127.0.0.1:9104  живой,   0 мс, лимит тела 59986 байт, роли: memorize

проверено 4 узлов, проблем 0
```

Если узлов не видно — они не запущены, или в адресе ошибка. Быстрая проверка
одного узла: `./bin/dcd --port 9101 --role compute` должен напечатать
`порт 9101, роли compute` и молча работать дальше.

## 4. Посмотреть план, не выполняя

```bash
./bin/dcctl plan "стоимость закупки 1250*3 и доля (1250*3+480)/7"
```

LLM вернёт шаги; вы увидите, какие роли и узлы подобраны, и ничего не выполнится.

## 5. Выполнить

```bash
./bin/dcctl run "стоимость закупки 1250*3 и доля (1250*3+480)/7"
```

```
Запуск плана (4 шагов, параллелизм 4, попыток на шаг 3)

  [»] s1   compute  192.168.1.10         стоимость закупки (98 байт)
  [»] s2   compute  192.168.1.11         доля части (114 байт)
  [+] s1   compute  192.168.1.10             -> 3750  (1 мс)
  [+] s2   compute  192.168.1.11             -> 604.2857143  (1 мс)
  [»] s3   verify   192.168.1.10         сверка суммы (193 байт)
  [+] s3   verify   192.168.1.10             -> OK  (0 мс)
  [»] s4   memorize 192.168.1.12         итог (175 байт)
  [+] s4   memorize 192.168.1.12             -> записано #4  (0 мс)

Итог:
  + s1   compute   192.168.1.10    3750
  + s2   compute   192.168.1.11    604.2857143
  + s3   verify    192.168.1.10    OK
  + s4   memorize  192.168.1.12    записано #4

Все шаги выполнены.
Каталог запуска: runs/20250114-101530
```

Артефакты запуска: `runs/<метка>/plan.json` (что собирались делать) и
`result.json` (что получилось).

## 6. Открыть панель

```bash
./bin/dcctl web --port 8080
```

Браузер: <http://localhost:8080>.

# Подключение LLM

Без LLM планировщик не работает: он не понимает естественный язык. Но есть три
пути, от самого простого к самому автономному.

## Вариант 1: облако (нужен ключ)

```bash
export OPENAI_API_KEY=sk-...
./bin/dcctl llm        # проверить, что сервер отвечает
./bin/dcctl run "посчитать 100*3"
```

Ключ можно не хранить в файле: `api_key = $OPENAI_API_KEY` подставит значение
из переменной окружения.

## Вариант 2: локальный сервер (без ключа)

llama.cpp server, Ollama, LM Studio, vLLM — любой OpenAI-совместимый endpoint.
Ключ не нужен: планировщик сам поймёт, что сервер локальный, и не пошлёт
`Authorization`.

```bash
# Ollama
ollama serve &
ollama pull qwen2.5:7b

# llama.cpp server
./llama-server -m model.gguf --port 8080 &
```

Конфигурация:

```ini
[llm]
url          = http://127.0.0.1:11434/v1/chat/completions
model        = qwen2.5:7b
api_key      =               # пусто — и этого достаточно
json_mode    = on
```

Проверка:

```
$ ./bin/dcctl llm
адрес:  http://127.0.0.1:11434/v1/chat/completions
модель: qwen2.5:7b
ключ:   не нужен (сервер свой)
спрашиваю: http://127.0.0.1:11434/v1/models

модели на сервере:
  -> qwen2.5:7b
     llama3.1:8b

готово: план можно строить (без ключа).
```

Если сервер в вашей сети, но не «локальный» по адресу, добавьте
`auth = none`. Свой ключ, если сервер его требует, отправляется всегда.

## Вариант 3: без LLM (эвристика)

```bash
./bin/dcctl run --no-llm "посчитать 1250*3 и долю (1250*3+480)/7"
```

Эвристика вытащит из цели арифметические выражения и построит
`compute… → verify → memorize`. Подходит для тестов и работы без сети.
`--strict` запрещает молчаливый откат на неё при сбое LLM.

## Что делать, если модель вернула ерунду

Планировщик не берёт план на веру: он проверяет его тем же кодом, что и
вручную написанный. Если план негодный (цикл в зависимостях, неизвестная роль,
обрезанный ответ), причина возвращается модели, и она пробует исправить —
две попытки. В лог это видно явно:

```
ERR   план от LLM отклонён: в графе шагов есть цикл (1 из 4 шагов упорядочимы)
info  прошу модель исправить план (попытка 2)
```

Совсем негодный ответ уходит в `runs/<метка>/plan.json`? Нет: туда попадает
принятый план. Непринятый можно увидеть в логе (`-v` покажет сырой ответ).

# Работа в командной строке

## Команды `dcctl`

| Команда | Что делает |
|---------|-----------|
| `init [ПУТЬ]` | создать образец конфигурации |
| `roles` | показать назначение ролей, лимиты и статистику узлов |
| `check` | опросить узлы: живы ли, что умеют, сколько памяти отдают |
| `discover [СЕК]` | найти узлы, объявляющие себя по широковещанию |
| `llm` | спросить у LLM список моделей: сервер жив, модель на месте |
| `plan "цель"` | построить план и показать, ничего не выполняя |
| `run "цель"` | построить план и выполнить |
| `run -f план.json` | выполнить готовый план |
| `replay МЕТКА` | повторить прошлый запуск по сохранённому плану |
| `runs` | список прошлых запусков с итогом |
| `shard gen\|info\|deploy\|run` | модель, разложенная по памяти устройств |
| `web [--host АДРЕС] [--port ПОРТ]` | веб-панель |

## Опции

```
  -c, --config ФАЙЛ     конфигурация (по умолчанию ./distcomp.conf, ~/.distcomp.conf)
      --role РОЛЬ=URL    назначить узла для роли (можно повторять)
  -f, --plan-file ФАЙЛ  исполнить готовый план
  -j, --concurrency N   одновременно выполняемых шагов
      --retries N       повторов при ошибке узла
      --timeout МС      таймаут одного узла
      --no-llm          не обращаться к LLM, построить план эвристикой
      --strict          не откатываться на эвристику при ошибке LLM
  -o, --out ДИР         куда сохранять plan.json / result.json
      --host АДРЕС      адрес веб-панели (по умолчанию 0.0.0.0)
      --port ПОРТ       порт веб-панели (по умолчанию 8080)
  -v, --verbose         подробный лог
      --color УРОВЕНЬ   цвет вывода: auto | always | never
  -V, --version         версия
  -h, --help            эта справка
```

**Глобальные опции пишутся до команды.** Исключение — `web`: у панели свои
опции, и привычно писать `dcctl web --port 8080`.

## Коды возврата

| Код | Значение |
|-----|----------|
| `0` | все шаги выполнены |
| `1` | есть незавершённые шаги |
| `2` | ошибка в аргументах |
| `3` | проблема с конфигурацией или недоступен сервис |
| `4` | план отклонён проверкой |

## Цветной вывод

Цвет включается сам, если stdout — терминал. В файле или в конвейере
управляющих кодов нет, поэтому вывод остаётся пригодным для `grep`:

```bash
./bin/dcctl run "..."            # в терминале — с цветом
./bin/dcctl run "..." | grep OK  # в конвейере — чистый текст
./bin/dcctl --color never run "…"
NO_COLOR=1 ./bin/dcctl run "…"
```

## История и повтор

```bash
$ ./bin/dcctl runs
Запуски в runs (новые сверху):

  20250114-104512   шагов 4 из 4   стоимость закупки и доля части
  20250114-101530   шагов 2 из 2   посчитать 6*7

Повторить: dcctl replay 20250114-104512

$ ./bin/dcctl replay 20250114-101530     # тот же план, другие узлы, свежий результат
```

Повтор полезен, когда узлы изменились: план уже утверждён, LLM не вызывается,
шаги просто уходят на те узлы, что живы сейчас.

## Свой план

Никто не мешает выполнить план, написанный руками:

```bash
cat > my.json <<'EOF'
{"goal":"проверка своими руками","steps":[
 {"id":"c1","role":"compute","title":"цена","payload":"100*3","deps":[]},
 {"id":"v1","role":"verify","title":"сверка","payload":"300","deps":["c1"]},
 {"id":"m1","role":"memorize","title":"итог","payload":"записать","deps":["v1"]}]}
EOF
./bin/dcctl run -f my.json
```

Шаг можно закрепить за конкретным узлом полем `node` — так делается раскладка
модели:

```json
{"id":"s1","role":"compute","title":"...","payload":"...","deps":[],"node":"10.0.0.7:9101"}
```

Перед выполнением план проверяется: роли назначены узлам, зависимости
существуют, граф ацикличен. Любое нарушение — понятная ошибка вместо молчаливого
неверного результата.

## Автоматизация

```bash
# ночной расчёт по расписанию
5 9 * * * cd /opt/distcomp && ./bin/dcctl -c distcomp.conf \
    run "стоимость закупки за вчера 1250*3, доставка 480" >> /var/log/dc.log 2>&1

# или через systemd timer — см. раздел про systemd выше
```

# Веб-панель

```bash
./bin/dcctl -c distcomp.conf web --host 0.0.0.0 --port 8080
```

Панель встроена в бинарник: никаких файлов на диске, кроме сохранённых планов.
Состояние опрашивается раз в 1.2 с.

## Что на ней есть

| Блок | Что показывает |
|------|----------------|
| Узлы по ролям | кто за какой ролью отвечает, задержка, лимит тела, память под модель, что узел уже держит из модели |
| Назначить узел | добавить или убрать узел роли прямо из браузера |
| Запуски | история с состоянием, выбор прошлого запуска |
| Параметры | модель, адрес LLM, нужен ли ключ, режим payload, параллелизм, повторы |
| Проверить LLM | кнопка: спрашивает сервер и показывает список моделей |
| Задача | цель на естественном языке |
| План и ход выполнения | таблица шагов: роль, зависимости, узел, состояние, результат, время |

## Правка плана перед запуском

Обычный путь: вписать цель → «Только план» → посмотреть, как LLM её разложила.

Если разложили не так, вкладка **«Правка плана»** показывает план обычным
текстом и выполняет то, что в нём написано, — LLM при этом не вызывается
вообще. Можно убрать лишний шаг, поменять формулу, закрепить шаг за узлом.

```
[Шаги] [Правка плана]                       ← Ctrl+Enter выполняет
┌────────────────────────────────────────┐
│ {                                      │
│   "goal": "стоимость закупки",         │
│   "steps": [                           │
│     {"id":"s1","role":"compute",       │
│      "payload":"1250*3","deps":[]},     │
│     …                                  │
│   ]                                    │
└────────────────────────────────────────┘
[Выполнить этот план]  [Вернуть план LLM]
```

## API панели

Если хочется управлять чем-то своим:

| Метод | Путь | Тело / параметры |
|-------|------|-----------------|
| GET | `/api/state` | — |
| GET | `/api/run?id=МЕТКА` | — |
| POST | `/api/run` | `{"goal":"…","execute":true}` или `{"plan":"{…}","execute":true}` |
| POST | `/api/role` | `{"role":"compute","url":"10.0.0.5:9101","op":"add\|remove"}` |

[role compute]

## Ключи `[llm]`

| Ключ | Значения | Смысл |
|------|----------|-------|
| `url` | URL | адрес chat/completions, OpenAI-совместимый |
| `model` | имя модели | что просим у сервера |
| `api_key` | строка или `$ПЕРЕМЕННАЯ` | ключ; можно оставить пустым для локального сервера |
| `auth` | `auto` \| `none` \| `bearer` | посылать ли `Authorization` |
| `style` | `openai` \| `anthropic` | формат запроса и ответа |
| `json_mode` | `auto` \| `on` \| `off` | требовать JSON-объект в ответе |
| `timeout_ms` | миллисекунды | сколько ждать ответа модели |
| `temperature` | число | 0 — детерминированно, что для планирования и правильно |
| `payload_mode` | `expr` \| `free` | что такое `payload`: арифметика или свободный текст |

## Ключи `[scheduler]`

| Ключ | Смысл |
|------|-------|
| `concurrency` | сколько шагов одновременно; больше — быстрее, но нагрузка на сеть |
| `retries` | сколько раз повторить шаг при ошибке узла |
| `timeout_ms` | сколько ждать ответа одного узла |
| `backoff_ms` | пауза перед повтором, равен `backoff_ms × номер попытки` |
| `outdir` | каталог для `plan.json` и `result.json` |

## Роли

Роли в конфигурации можно назвать как угодно (`[role gpu]`), но тогда узел должен
уметь обслуживать именно это имя. Встроенный `dcd` понимает четыре:

| Роль | Что делает |
|------|-----------|
| `compute` | считает арифметическое выражение из `payload` |
| `verify` | сверяет: `payload = all` — все результаты непустые; число — один из результатов должен совпасть |
| `memorize` | дописывает JSONL-запись в `state/memory.log` |
| `shard` | держит свои слои весов и считает ими по активациям |

# Узлы: запуск и роли

```bash
./bin/dcd --role compute --role verify --port 9101 --tag pi-1 --state /var/lib/distcomp
```

| Опция | Значение | Смысл |
|-------|----------|-------|
| `--role` | compute \| verify \| memorize \| shard | можно повторять: один процесс — несколько ролей |
| `--port` | 1–65535 | порт службы узла |
| `--tag` | строка | имя узла в отчётах и панели |
| `--state` | каталог | куда пишет `memory.log` |
| `--max-body` | байт | сколько байт задачи узел примет (по умолчанию 59986, у lite 1024) |
| `--free-mem` | байт | сколько весов модели узел отдаёт (по умолчанию — свободная память машины) |
| `--hello-interval` | секунд | как часто объявлять себя по сети, `0` — не объявлять |

## Как узлы находятся сами

Узел рассылает объявление при старте и раз в `--hello-interval` секунд. Чтобы не
ждать, планировщик спрашивает сеть активным запросом:

```bash
$ ./bin/dcctl discover 5
Слушаю объявления узлов 5 с (Ctrl-C — прервать)…
  192.168.0.101   :9101   pi-1     compute,verify      лимит  59986 байт  x86_64
  192.168.0.101   :9102   mcu-01   compute,memorize    лимит   1024 байт  x86_64

найдено объявлений: 2
добавьте нужные строки в конфигурацию, например:
  [role compute]
  daemon = 192.168.1.50:9101
```

Скопированные строки вставьте в конфигурацию — или назначьте узлы из панели.

## Как выбирается узел

- Шаги с готовыми зависимостями стартуют одновременно, максимум `concurrency`.
- Внутри роли берётся узел с наименьшим числом текущих задач; при равенстве —
  по кругу, так что простаивающие узлы загружаются равномерно.
- Узел, который не примет задачу по размеру, исключается заранее: лимит
  известен из первого PING.
- Упавший узел не убивает задачу: идёт повтор с задержкой, и на следующей
  попытке шаг может взять другой узел той же роли.

## Один узел — несколько ролей

На устройстве с 40 КБ ОЗУ три процесса не запустить, а один с тремя ролями
помещается:

```bash
./bin/dcd --role compute --role verify --role memorize --port 9101 --state state
```

# Модель, разложенная по устройствам

Вес модели — почти целиком VRAM. Модель, не помещающаяся в Raspberry Pi с 8 ГБ,
раскладывается на него и на две платы ESP32: слои режутся, кладутся на
устройства по их свободной памяти, а по сети идёт не модель, а активация.

## Четыре команды

```bash
./bin/dcctl shard gen model.bin 6 8     # демо-модель: 6 слоёв шириной 8
./bin/dcctl shard info model.bin        # что куда помещается
./bin/dcctl shard deploy model.bin      # раздать веса по узлам
./bin/dcctl shard run model.bin 1 2 3 4 5 6 7 8   # прогнать вектор
```

Устройства берутся из секции `[role shard]`, память — из ответа на PING.

## Пример с микроконтроллером

```bash

# сервер: по умолчанию отдаст всю свободную память
./bin/dcd     --role shard --port 9103 --tag board-1 --state state
```

```ini
[role shard]

daemon = 127.0.0.1:9103
```

## Формат модели

Файл — последовательность слоёв, у каждого заголовок и веса:

```
"DCSH" | u32 index | u32 dim_in | u32 dim_out | u32 act
f32 W[dim_out × dim_in]        (по строкам)
f32 b[dim_out]
```

`act`: 0 — `tanh`, 1 — ReLU, 2 — линейный. Всё float32, little endian.
Формат тот же, что даст конвертер настоящей модели: отличается только
содержимое.

## Границы

Считает эталонная реализация (стек полносвязных слоёв), а не llama.cpp: механика
раскладки, заливки и пересылки активаций — настоящая, а вот чтобы считать
настоящей LLM, `role_shard` в `src/daemon.c` нужно заменить вызовом движка.
Всё остальное — раскладка, заливка, конвейер, сверка — остаётся как есть.

# Маленькие устройства

```bash
make lite     # -> bin/dcd-lite
make size
```

Сборка lite: без потоков, без `malloc` (все буферы в BSS), `-Os`, дейтаграмма
1200 байт, приём тела 1024 байта, пул под модель 8 КБ. Бинарник — около 45 КБ
вместе с libc. Цель: SAMD51, RP2040, ESP32, STM32.

Что планировщик знает про маленький узел и не делает:

- не пришлёт задачу тяжелее лимита тела узла;
- не положит в него больше весов, чем тот сам объявил;
- смешанный парк работает сам: в одной роли может быть и сервер, и плата,
  мелкие шаги распределятся по обоим, тяжёлые уйдут туда, где есть лимит.

Смешанный парк проверяется в тестах (сценарий 14) и в демо-стенде.

# Что делать, если не работает

| Симптом | Причина и что делать |
|---------|----------------------|
| `ни одной роли не обеспечено узлом` | в конфигурации нет ни одного `daemon`; проверьте `dcctl roles` |
| `узел не слушает порт (ICMP unreachable)` | на этой машине узел не запущен или порт занят: `ss -ulnp \| grep 9101` |
| `задача N байт не помещается ни в один узел роли …` | все узлы роли маленькие; добавьте узел побольше или разбейте шаг |
| `шаг закреплён за узлом …, но он не взял задачу` | узел изменился или перегружен; уберите `node` из шага или поправьте адрес |
| `в графе шагов есть цикл` | так бывает в плане от LLM: план не выполнен, поправьте `deps` и повторите |
| `план не является корректным JSON` | смотрите сырой ответ модели: `./bin/dcctl -v plan "…"` |
| `сервер не отвечает: таймаут N мс` | неверный адрес LLM или она думает дольше таймаута; поднимите `timeout_ms` |
| `сервер ответил HTTP 401` | нужен ключ: задайте `api_key` либо `auth = none` для своего сервера |
| `сервер не локальный, а ключ не задан` | добавьте `api_key = $OPENAI_API_KEY` или `auth = none` |
| `в узле не хватает памяти для слоя` | поднимите `--free-mem` или добавьте устройство |
| в панели «предыдущий запуск ещё идёт» | дождитесь конца или откройте другую вкладку; запуски по одному |
| узлы не находятся через `discover` | широковещание может быть запрещено сетью; укажите узлы вручную |

Подробный лог: `./bin/dcctl -v …`. Проверить узлы по одному: `./bin/dcctl check`.

# Подробности

## Роли и что делает встроенный узел

| Роль | Что делает |
|------|-----------|
| `compute` | считает арифметическое выражение из `payload` |
| `verify` | сверяет: `payload = all` — все результаты непустые; число — один из результатов должен совпасть |
| `memorize` | дописывает JSONL-запись в `state/memory.log` |
| `shard` | держит свои слои весов и считает ими по активациям предыдущего |

## Формат плана

LLM обязана вернуть такой JSON (клиент снимает markdown-ограждения сам):

```json
{
  "goal": "стоимость закупки и доля части",
  "steps": [
    {"id":"s1","role":"compute","title":"стоимость закупки","payload":"1250*3","deps":[]},
    {"id":"s2","role":"compute","title":"доля части","payload":"(1250*3+480)/7","deps":[]},
    {"id":"s3","role":"verify","title":"сверка","payload":"3750","deps":["s1","s2"]},
    {"id":"s4","role":"memorize","title":"итог","payload":"итоговая сумма","deps":["s3"]}
  ]
}
```

Результаты шагов передаются зависимым в поле `context`, поэтому `verify` имеет
под рукой то, что вычислили `compute`.

## Протокол демона

Узел — это любой процесс, который отвечает на UDP-порт и понимает заголовок
из `src/udp.h`. Заголовок 14 байт, big endian:

```
  смещение  размер  поле
     0        2     magic = 0x4443 ('D','C')
     2        1     версия протокола (2)
     3        1     тип сообщения
     4        2     флаги (бит 0 — тело в JSON)
     6        4     длина тела
    10        4     CRC32 тела
    14        N     тело (JSON, UTF-8)
```

Типы: `REQUEST=1`, `RESPONSE=2`, `PING=3`, `PONG=4`, `HELLO=5`, `WELCOME=6`.

Запрос:

```json
{"role":"compute","title":"...","payload":"1250*3","attempt":1,
 "context":[{"from":"s1","role":"compute","output":"3750"}]}
```

Ответ:

```json
{"ok":true,"output":"3750","detail":"1250*3 = 3750",
 "node":"pi-1","max_body":59986,"free_mem":1048576,"roles":"compute,verify"}
```

`ok:false` означает провал шага: планировщик повторит его `retries` раз, а
зависимые шаги пометит заблокированными. Ответ на `PING` — `PONG` с тем же
набором полей.

## Формат выражений

`payload` в режиме `payload_mode = expr` — арифметика: `+ - * / % ^`, скобки,
унарный минус, функции `sqrt abs min max pow floor ceil round sign sin cos tan
asin acos atan exp log log2 log10 atan2`, константы `pi e tau`, запятая как
разделитель аргументов функции и `_` как разделитель разрядов внутри числа
(`1_000_000`). Пример: `(1250*3+480)/7`.

Если `payload_mode = free`, LLM получает другое указание и `payload` становится
произвольным текстом — этот режим для демонов, которые занимаются чем-то
сложением арифметики.

## Планирование: LLM, починка и эвристика

Запрос к модели — один, с системным промптом, в котором перечислены доступные
роли, их узлы и реальные лимиты тела. Дальше план **проверяется тем же кодом,
что и вручную принятый**: цикл, несуществующая зависимость, неизвестная роль,
обрезанный ответ (`finish_reason=length`) — всё это не «план», а отказ.

На отказ модель не выбрасывается: ей отправляется её собственный прошлый ответ и
точная причина, и она пробует исправить. Попыток две. Только после этого —
эвристика, и то лишь если не задан `--strict`.

## Как распределяется нагрузка

- Шаги с готовыми зависимостями стартуют одновременно, максимум `concurrency`.
- Внутри роли выбирается демон с наименьшим числом текущих задач; при равенстве
  — по кругу.
- Узел, который не примет задачу по размеру, заранее исключается из выбора.
- Упавший узел не убивает задачу: повтор с задержкой, и на следующей попытке
  задачу может взять другой узел той же роли.
- Зависимые шаги запускаются только после успешного завершения зависимостей.
